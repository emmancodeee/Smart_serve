# MongoDB ERD

This project uses MongoDB, so the diagram below shows logical relationships between collections and embedded subdocuments rather than SQL foreign-key constraints.

## Mermaid ERD

```mermaid
erDiagram
    USER {
        ObjectId _id PK
        string name
        number age
        date birthday
        string studentNumber UK
        string email UK
        string password
        string fullname
        string pictureOfId
        string module
        string uniformType
        string books
        string course
        boolean isAdmin
        string status

        string lastLoginIp
    }

    ADMIN {
        ObjectId _id PK
        string name
        string email UK
        string password
        boolean isAdmin
        boolean isSuperAdmin
        date lastLoginAt
        string lastLoginIp
    }

    AUTH_CODE {
        ObjectId _id PK
        string email
        string purpose
        string code

    }

        ObjectId _id PK
        string itemName

    REGISTRATION {

        string category

    SCHEDULE {
        ObjectId _id PK
        ObjectId userId FK
        string title

        date rescheduleAdjustedAt
        date rescheduleCompletedAt

    TRANSACTION {
        ObjectId _id PK

        string adminModel
        string adminName
        string action
        string entityType
        string entityId

    }

    USER ||--o| REGISTRATION : "owns current registration"
    USER ||--o{ SCHEDULE : "has schedules"
    REGISTRATION ||--o{ REGISTRATION_ALLOCATION : "embeds allocations"
    INVENTORY ||--o{ REGISTRATION_ALLOCATION : "allocated from"
    SCHEDULE ||--o{ SCHEDULE : "rescheduled from originalMissedScheduleId"
    ADMIN ||--o{ TRANSACTION : "writes admin logs"
    USER ||--o{ TRANSACTION : "writes legacy admin logs"
    USER ||..o{ AUTH_CODE : "matched by email"
    ADMIN ||..o{ AUTH_CODE : "matched by email"
```

## Notes

- `REGISTRATION_ALLOCATION` is an embedded array inside the `Registration` document, not a separate MongoDB collection.
- `AuthCode` is linked to `User` and `Admin` by `email`, not by `ObjectId`.
- `Transaction.adminId` is polymorphic through `adminModel`, so it can reference either `Admin` or a legacy admin stored in `User`.
- `User -> Registration` behaves like one-to-zero-or-one in service logic, although the schema does not enforce a unique index on `Registration.userId`.
- `Schedule.originalMissedScheduleId` is a self-reference used for reschedule history.
